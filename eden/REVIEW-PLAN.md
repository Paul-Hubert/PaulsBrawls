# Eden — Deep Review Plan

A plan for a thorough, adversarial review of **Eden** (the `eden/` Node subsystem): the
LLM-driven Minecraft village brain (one God × ten villagers over one God-owned skill library).
Goal: surface **architectural flaws, bugs, unexplained/risky code, and claim↔reality drift**.

Scope: `eden/` and `docs/` only. Out of scope: the Java Fabric mod (`src/`), v1
(`minecraft-mcp-server/`) — except at the two seams Eden depends on (settlement `:8767`, op-on-join).

---

## 0. Review posture (why this codebase needs a *specific* kind of skepticism)

Three facts shape every workstream below:

1. **It is exhaustively self-documented.** Comments are long, confident, and reference invariants
   (R-numbers, D-numbers, "gap W/Z"). **Treat every load-bearing comment as a claim to verify, not a
   fact to trust.** The highest-value findings are where the prose asserts a guarantee the code does
   not actually deliver.
2. **CI is green on fakes only.** `npm run check` never touches Minecraft; the FakeBot models a
   *subset* of mineflayer. The live-test findings already filed (W, Z, C, D1, D2, E) are all
   fakes-passed / real-broke. **The fakes↔real-mineflayer gap is the prime bug habitat** — anything
   validated only against `tests/fakes/fake-bot.ts` is suspect on the real API.
3. **It was generated by an LLM.** Expect: plausible-but-shallow validation, mechanisms that are
   *described* completely but *wired* partially, defensive `catch {}` that silences the very signal
   the architecture says is sacred, and "by design" labels on genuine risks.

The review is **claim-driven**: for each invariant the docs promise, find the code that enforces it,
then try to break it.

---

## 1. Deliverable & finding format

Produce a single findings report, severity-ranked. Each finding:

```
[SEV] <one-line title>                        SEV ∈ {Critical, High, Medium, Low, Nit}
  Location:  <file:line> (+ related)
  Claim:     <what a comment/doc/test asserts is true>     (omit if no claim)
  Reality:   <what the code actually does>
  Impact:    <concrete failure mode — host freeze / wrong verdict / data loss / silent drift>
  Repro/Evidence: <test idea, journal query, or live scenario that would demonstrate it>
  Fix sketch: <smallest correct change>
```

Severity rubric for *this* system:
- **Critical** — can wedge/crash the single host process, corrupt the journal (the source of truth),
  or exfiltrate the API key.
- **High** — produces wrong God verdicts, breaks the refinement loop's convergence, or silently
  drops events the architecture promises are durable.
- **Medium** — claim↔code drift on a load-bearing invariant; correctness gap that degrades quality
  but self-heals or is bounded.
- **Low/Nit** — dead params, misleading comments, style, cheap robustness.

---

## 2. Method (techniques to apply in every workstream)

- **Comment-vs-code diffing.** Read the comment's promise, then read the code under it line by line.
- **Fakes-fidelity check.** For each subsystem, open the matching `tests/fakes/*` and ask: *what does
  the fake model that real mineflayer does differently?* (positions as plain objects vs `Vec3`,
  synchronous vs packet-delayed block changes, missing events, `bot.registry` shape — see R55, Z, D1).
- **Journal-replay as oracle.** `npm run rebuild-stats` must equal the live fold (`views/index.ts`).
  Any writer/reader asymmetry is a derived-state bug. Audit every `views/` fold against every
  `journal.append` site for that kind.
- **Async/lifecycle tracing.** Every `setInterval`/`setTimeout` (is it `unref`'d? cleared on every
  exit path?), every `void promise` (unhandled rejection?), every `.catch(() => {})`.
- **R# traceability.** `docs/07-hard-won-lessons.md` claims R1–R61 are "pinned by tests." Spot-check:
  pick 10 R's, find the test that actually pins each, confirm it asserts the behavior (not just runs).
- **Single-writer audit (S2).** The curriculum is the sole ledger writer; the journal is append-only.
  Grep every mutation site and confirm the invariant.

## 3. Workstreams

Each can be reviewed independently (good fan-out boundaries). Files listed are the entry points.

### A. Skill execution engine + instrumentation  ★ highest risk
`src/skills/engine.ts` · `src/skills/instrument.ts` · `src/bots/hardening.ts`

The host's safety perimeter. Verify, don't trust:
- **Loop-budget coverage holes.** `instrument()` injects `__loopBudget()` only into *explicit loop
  statement* bodies. Confirm what happens with: synchronous infinite **recursion**; a spinning
  `Array.forEach`/`map`/`reduce`/`while`-free callback; `for await…of` (is the implicit await wrapped
  by `__aw`?); generators. These are the "answer to `while(true)`" the mechanism exists for — find
  the ones it misses and whether they freeze the host.
- **Macrotask canary reach.** `checkProgress` only runs *inside instrumented loop bodies*. A sync spin
  with no loop node is invisible to it AND to the (starved) wall timer/stall detector. Map the gap.
- **Sandbox porosity vs the security claim.** The shim shadows `process`/`require`, but
  `globalThis.process`, the `Function` constructor, dynamic `import()`, `fetch`, `Buffer`,
  `setTimeout/Interval` are all reachable. Docs call this "by design; tier gate is the only boundary."
  Pressure-test that acceptance — especially **`globalThis.process.env.OPENAI_API_KEY` exfiltration**
  from LLM-authored skill code (see Workstream L).
- **Abort protocol correctness.** Trace `EngineAbort` → `abortActiveTasks` (R4/R5 order:
  collectblock→pvp→pathfinder stop() then setGoal(null)→window→settle). Confirm every timer is
  cleared on every exit path of `executeTree` (timeout, stall, preempt, throw, normal).
- **`captureSnapshot` is mostly stubbed** — `biome:'unknown'`, `time:0`, `equipment:[]`,
  `nearbyEntities:[]`, `nearbyBlocks:[]`, `knownChests:[]`. These become `worldBefore/worldAfter` in
  every `RunReport`, which the docs say is core critic input. **Determine whether the critic's
  world-delta judgment is effectively blind to terrain/entities/equipment**, or whether a richer
  snapshot is assembled elsewhere (`render/snapshot.ts`). If blind, the critic is overstated.
- **`validateArgs` is shallow & non-recursive** — top-level `type` + `required` only; no nested
  object/array-item checks, no enum/min/max/additionalProperties. The comment promises "boundary
  errors that can't lie." Quantify what slips through for any skill with structured params.
- **Probation graduation counts but never re-judges.** The comment admits the "auto-ticket for
  re-review" of D-12 is unbuilt. Confirm and assess: does the documented 3-rail safety actually have
  only 2.5 rails? `BotRunQueue.currentAbort` takes a `cause` arg that's never used (dead param).

### B. The refinement loop (the production pump)  ★ high risk
`src/main.ts` (`RolloutCoordinator` ~862, `VillageLoop` ~1043, `start()` ~107, `wireGod` ~486)

This is where wiring bugs and convergence failures live (memory: R54 idle-loop, R67/R68 hot-spin).
- **Idle/backoff correctness.** `VillageLoop.drive` (~1110): confirm `if (!result) backoff =
  idleBackoffMs` actually prevents the hot-spin that R68 was, on *every* "nothing to do" path
  (no directive, curriculum returns nothing, body not connected, preempted).
- **The density invariant (D-11).** Docs: the revision prompt carries full draft + verbatim error +
  rendered world + critique in ONE never-trimmed message; older revisions trim oldest-first;
  `write_skill` source-caps so the payload always fits the tier budget. Find the assembly site and
  the trimming logic — prove the *current* payload is never trimmed and that the size cap math is
  correct against `strongInputTokenBudget`.
- **Composition-root justification.** `RolloutCoordinator`/`VillageLoop` live in `main.ts` to dodge
  the dependency law (they touch god/ + villagers/). Confirm they genuinely can't be a layer-3 module
  and that `main.ts` (1181 lines) isn't hiding logic that belongs under test.
- **Lifecycle.** `reactivityTick` interval (~221), `void pool.start()`, `epoch` guarding on
  `restart` (R66 kick-storm) — confirm clean teardown in `stop()` and no orphaned loops on restart.

### C. God desks
`src/god/{god,critic,curriculum,orchestrator,body}.ts` · `src/god/prompts/*.md`

- **Critic verdict integrity.** What inputs does it actually receive (tie to A's stub-snapshot
  finding)? Can a malformed/hallucinated verdict admit a bad skill? Is the one-directional `check`
  veto real? Does "interventions teach, never do the task → critic voids divine-completed tasks"
  exist in code?
- **Curriculum = sole ledger writer (S2).** Grep every ledger mutation; confirm no other writer.
  Verify R67 (proposal context now includes inventory + existing skills) and R68 (`tool_choice`
  forced on `proposeTask`/`decompose`) are actually in the prompt-build code, not just in memory.
- **Prompt golden tests (S6).** Docs claim prompts have golden snapshot tests. Confirm they exist and
  would catch drift; check the `combineDesks` cheap-mode path isn't untested.
- **Desks share state, never a context window (D-06).** Confirm in code.

### D. Library, versioning & retrieval
`src/skills/{library,retrieve,describe,exemplars/index}.ts`

- **State machine** `draft → active-probation → active`, append-only versioning, quarantine,
  `autoQuarantineAfter` tripwire — verify transitions and that files are never deleted.
- **Retrieval correctness.** Embedding retrieval + keyword fallback; ~6 exemplars as full code,
  rest as signatures; divine skills invisible to mortal retrieval (R25). Confirm the tier filter.
- **Exemplar/stock-skill real-mineflayer correctness** (896 lines — the biggest single file). These
  are validated against FakeBot. Cross-check against the Z/C/E/R55 findings: `Math.hypot` not
  `Vec3.distanceTo` (memory), `ctx.Vec3`/`ctx.goals` usage, read-after-write races (till/sow).
  This file is where a fakes-passed/real-broke bug is most likely to still hide.
- **Dedup.** Runtime `.eden-data/library/` was deduped 173→27 (memory) — is the dedup logic in code
  or a one-off? Can duplicates regrow?

### E. Villager runtime
`src/villagers/{brain,events,subscriptions,context-pack,memory,memory-summarizer,drives,reactivity,role-defaults,tools,inbox}.ts`

- **Event hysteresis (in the emitter).** `events.ts` (415 lines): confirm edge events
  (`health-low`, `night-falls`) carry hysteresis so subscribers never flap. `bots/signals.ts`
  derives hurt from health-delta (memory M5) — check the threshold/debounce.
- **Subscriptions = filters-as-data (P5).** No predicate code; AND-composed clauses. Confirm the
  evaluator is data-driven and `notWhileRunning` reads the live `runningSkills()`.
- **Context pack (8 ordered sections, per-section token ceilings).** Verify deterministic assembly,
  that section sizes are journaled, and that §6 MÉMOIRE actually pre-loads from `retrieve` (R69).
- **Memory.** Window→archive→summarization; ranked retrieval `0.5·rel + 0.25·rec + 0.25·imp`;
  world-stamp quarantine on host:port mismatch (R32). Confirm `recall`/`remember` tools are wired
  (R69 fixed this) and that the social-conversation→memory write gap noted in R69 is closed or filed.
- **`run_skill` is the only world-effect path (P2).** Confirm no direct micro-action tool leaked in.

### F. Journal, views, observability  ★ correctness oracle
`src/journal/{journal,kinds,lag-monitor}.ts` · `src/views/index.ts` · `src/cli/rebuild-stats.ts`

- **Journal write durability.** `journal.ts:146` swallows in a `catch {}` — **the journal is the
  source of truth; a silenced write failure is a Critical-class data-loss bug.** Audit it.
- **Fold parity.** Every `views/` reducer must be reconstructable by replay. Diff live fold vs
  `rebuild-stats` for each derived view (skill stats, dossier, relations, ledger, rollout index).
- **Backpressure (D-07).** Synchronous WAL writes + "never journal the hot stream (pulses are
  in-memory)". Confirm pulses are truly never appended and the lag-monitor canary fires at
  `max ≥ 1000ms`.
- **`refs` causality column.** Confirm every append sets `actor` + `refs` so causality is queryable.

### G. Bots layer + the fakes↔real seam  ★ high risk
`src/bots/{pool,anchors,hardening,signals,plugins,helpers}.ts` · `tests/fakes/fake-bot.ts`

- **Pool identity (R66).** Handlers keyed by bot-instance not name; restart kick-storm fix — confirm
  the identity guards and the 4s stagger (I1).
- **Anchors self-heal (R18).** `home`/`chest` hints snap to real ground; two `catch {}` (170, 182) —
  what failure do they hide?
- **Plugin loading.** Named imports for the CJS trio (R15); `catch (err)` at plugins.ts:71.
- **The fakes gap, enumerated.** Produce an explicit table: *mineflayer API surface the stock skills
  and engine use* × *what FakeBot models* × *real behavior*. This table is itself a deliverable and
  predicts the next live-test finding.

### H. Social
`src/social/{conversation,trade}.ts` · `tests/fakes/fake-settlement.ts`

- Trade settlement POST to Java `:8767` — confirm atomicity assumptions, failure handling, and that

- Mirror-gating of bot↔bot chat to game chat — confirm no command-injection via chat (ties to L).
- Confirm the R69 gap (conversation not writing memory) status.

### I. Admin API + website
`src/admin/server.ts` · `eden/website/*`

- **Localhost-only?** Confirm the HTTP + WS server binds loopback, not `0.0.0.0`. Mutating verbs
  (`prompt`, `pause`, `quarantine`) must journal `actor` BEFORE acting — verify, and check authz
  (any local process can drive the village).
- **Four `catch {}` (119, 220, 317) + `catch(err)` (157)** — what do they hide; do route errors leak
  stack/secrets?
- **Website is a pure consumer** (memory: mock-api deleted). Confirm `website/api.js` is the only data
  source and the `/journal` RAW-shape seam matches `kinds.ts` (replay/ui.js depend on it).
- **`HTTP_1_1` pin** for the Java→Eden `/villagers` call (memory: h2c-upgrade reset). Confirm the
  server doesn't offer an upgrade that breaks JDK HttpClient.

### J. Config, identity, ports, scenario loading
`src/config.ts` · `src/scenario-loader.ts` · `src/providers.ts` · `eden.example.json` · `roles.json`

- **Secret hygiene.** Key is env-only, never written to config/journal; `redactSecrets` (main.ts
  ~1130) — confirm it redacts in *all* paths that could log a prompt/config (admin, debugPrompts,
  llm transcripts `.eden-data/llm/*.json`).
- **Identity uniqueness (R12).** `Dieu` + French roster + `EvalBot*` namespacing — confirm no
  username collision across coexisting systems is possible from config defaults.
- **Scenario override gotcha** (memory): `scenario` in config overrides the `villagers` roster — a
  surprising precedence; confirm it's intentional and documented.
- **Config validation.** Does a malformed `eden.json` fail loudly with a useful error, or silently
  default?

### K. Concurrency & async correctness  (cross-cutting)
- Enumerate every `setInterval`/`setTimeout`: `unref`'d? cleared on shutdown? (reactivityTick,
  heartbeat, sampler, stall timer, sleep ticks, lag monitor, scheduler).
- Every `void <promise>` and `.catch(()=>{})`: can it swallow a fatal? `installProcessGuards`
  (main.ts ~1151) is the backstop — confirm it journals and doesn't mask test failures (opt-in only).
- Scheduler (`llm/scheduler.ts`): concurrency cap, priority lanes, per-villager cooldown, coalescing,
  God preemption, **rollout immunity** (revision turns bypass suppression). Prove the immunity path
  can't be starved and the cap is actually enforced under burst.
- LLM client (`llm/client.ts`): 5 `catch` sites (181, 228, 263, 324, 349) — retry/timeout/abort
  semantics; does a provider 429/500 escalate or silently degrade?

### L. Security posture  (cross-cutting)  ★ surface the accepted-but-undocumented risk
The threat model is unusual: **skill *code* is LLM-authored from prompts that include world chat,
player names, and retrieved memory.** That is an injection channel into code that runs with full Node
capability in the host process.
- **API-key exfiltration.** Trace whether a villager-authored skill can reach
  `globalThis.process.env.OPENAI_API_KEY` (or `fetch` it out). If yes, document the blast radius and
  whether the "tier gate is the only boundary" stance accounts for it.
- **Prompt injection → skill author.** Can chat/memory content steer `write_skill` into hostile code?
  What stops it? (Critic judges *behavior*, not safety of the code text.)
- **Settlement/coin abuse.** Can a skill mint/transfer coins via the settlement endpoint outside the
  trade protocol?
- Frame each as either a real finding or an explicit, documented risk acceptance — the current docs
  assert the posture without enumerating these consequences.

### M. Test quality & coverage honesty
`tests/**` (66 files) · `eval/**` · `live-tests/**`

- **Coverage is ~94%/83% on fakes.** High line coverage with low-fidelity fakes is a false comfort.
  For each `*-coverage.test.ts`, check whether it asserts behavior or just executes lines.
- **R# pinning audit** (per §2). Find R's claimed-pinned but not actually asserted.
- **Live-test gaps.** Only 3 scenarios; `craft-wooden-tools` was "pending funded re-run" (memory).
  Identify which architectural claims have *no* live coverage (e.g., multi-villager trade, God
  intervention voiding, quarantine self-heal, memory world-stamp migration).
- **Parity test** (`tests/parity.test.ts`) — what does it actually compare?

## 5. Suggested execution

- **Sequence:** A → F → B → C/D → E → G → K/L (cross-cutting) → H/I/J → M/N. A and F first because they
  define the safety perimeter and the correctness oracle; everything else is judged against them.
- **Parallelizable:** A, C, D, E, G, H, I are independent file sets — good for fan-out (one reviewer/
  agent each) with a shared findings format. K, L, M, N are cross-cutting synthesis passes done after.
- **Two oracles to lean on:** (a) `rebuild-stats` vs live fold for any state question; (b) a live-test
  run (real server + key) for any fakes-fidelity question — the fakes will not catch these.
- **Effort:** ~1–1.5 days solo for a credible pass over A–N; the engine/instrument/main trio (A,B) and
  the fakes-gap table (G) are where time is best spent.
